这篇 Playbooks 要回答的是一个很具体的问题：在 Claude 平台或 Claude Code 里做日常开发，该从哪一个模型起步，又该在什么时候换。当前一般可用的四个模型是 Claude Haiku 5.5、Claude Sonnet 5.5、Claude Opus 5.5 和 Claude Fable 5.2。另有一个 Claude Mythos 5.2，原文称它是网络安全与生命科学研究上「最强」的模型，但只通过验证项目提供，不在这篇的日常选型里。

原文配了几段演示视频：用四个模型把同一张巷子照片写成绘画程序、并排搭同一个作品集站点、用 Fable 5.2 把一个场景画成十六种渲染风格，以及四个模型同时改一家网店。演示分别署名 Lance Martin、Addy Osmani、Dan Fein。按版权条款与本站惯例，这些视频和原图都没有下载或转载。

先记住的结论

作者给的快答是：多数工作从 Opus 5.5、默认的 medium effort 开始。原文原句是：

The quick answer is that you should start most work on Opus 5.5 at its default effort level, medium.

— Addy Osmani，Which Claude model should you build with?（claude.dev，2026-11-09）

它是 Claude Code 的默认模型，输入和输出的每 token 标价是 Fable 5.2 的一半，也被推荐为大多数编程与知识工作的起点。

再往下分三步：

  • 任务边界清楚、属于日常修复或按规格做功能，可以下探到 Sonnet 5.5。但「有清晰规格」并不自动等于该用 Sonnet：迁移或性能优化完全可能规格清楚、难度仍高，这时仍应用 Opus 5.5；重大项目则上探 Fable 5.2。
  • 再往下，分类、路由、抽取这类最简单、量大的工作，以及给大模型打下手的子智能体，用 Haiku 5.5。
  • 往上，编码、金融与科学里最难的技术项目，或者 Opus 5.5 开到 high 仍然不够，以及长时间无人值守的运行，再用 Fable 5.2。

换模型之前，先试着调 effort。它是更细的成本和能力旋钮。超过 high 之后，再升一档 effort，花费可能已经接近换一个更大的模型，所以要在自己的任务上两边都比一比；若已经超过 high，下一步应拿更大的模型、用更低的 effort 来测。反过来，降一档或许就能在更低费率下得到需要的结果。

更高的 effort 适合模型需要想更久、多调用工具、或多做自我检查的时候，但也会增加延迟。它不会凭空补上模型本身没有的知识或技能——那种情况仍然要换更大的模型。

三组权衡

能力，以及「做完一件事」的成本

更大的模型通常每 token 更贵、也更强，但放到具体任务上并不总是如此。作者的原句是：「A higher price per token doesn't always mean a higher cost per task, or a better result.」

原文举了几组 Anthropic 自己跑的基准，均为自报 ⚠️（核于 2026-11-10），本站未复现：

  • 在 Terminal-Bench 3.0 上，上一档 Fable 5.1 开到 max 得 58.0%；Opus 5.5 开到 high 得 58.9%，而且用了一半的 token。出处是姊妹篇 Spending your effort。
  • 在更难的 FrontierCode 2.0 上，Fable 5.2 开到 high，与 Opus 5.5 开到 max 大致持平（45.3% 对 45.5%），但每项任务成本大约只有一半。所以：难题上先不要把 Opus 5.5 推过 high，先拿 Fable 5.2 比一比。日常工作仍从 Opus 5.5 的 medium 起。更完整的成绩见 Fable 与 Mythos 5.2 发布文。
  • 比较两个模型时，既要给典型任务定价，也要给集合里最难的那些定价，因为花费往往集中在最难的几项。原文提到一项 20 题的搜索基准里，两道题就占了 43% 的花费 ⚠️。

平台文档里的成本与智力测量也显示：小模型适合输出可核对、通量高的工作，不太适合很长的智能体循环。

延迟对准确

更快的配置更早结束，也可能错过更多。人选模型和 effort 之前，先想清楚人能等多久。等人看着的回复，从 Sonnet 5.5 的 low 或 medium 起。

原文称新生代往往比前辈更快：Fable 5.2 的输出速度最多比 Fable 5.1 快 30%；Sonnet 5.5 比 Sonnet 5 快 30%。⚠️ 厂商自报，未独立测速。

effort 与延迟大致同向。要以多出来的准确，值不值得多等那一段时间。原文在 SWE-bench Pro 上的对照（⚠️ 自报）：Opus 5.5 的 medium 比 high 大约低 2.5 分，成本约是其 70%；low 大约低 8 分，成本约是三分之一；xhigh 大约高 1.4 分，成本是 high 的 2.5 倍。

作者更看重的一步是：先给模型一种自我核验的办法（测试、构建，或调用接口的脚本），这往往比改 effort 更省钱、也少增延迟。模型不够用时，按这个顺序试：先确认它能核验自己的工作；再把 effort 升一档；再换更大的模型，并且从比刚才更低的 effort 起测。

如果结果可以自动检查，就先全部用低档跑，只把失败的再用高档重跑。同一份 SWE-bench Pro 子集上，Opus 5.5 以 low 起步、失败项再以 high 重跑，约通过 97%，每项约 $0.17；全部直接 high 则是 95.3%、每项约 $0.29。⚠️ 自报。

若要在不放弃能力的前提下加快同一模型的回复，Opus 5.5 和 Fable 5.2 在 Claude API 上提供 fast mode，输出更快，按溢价计费。

上下文对成本

这一代四个模型的上下文窗口都是 1M token。更大的上下文有助于做完任务，但每一轮都会把上下文再送一遍。长运行里，大部分输入会按缓存读取计费。

缓存读取价：Opus 5.5 与 Fable 5.2 都是每百万 token $0.20，Sonnet 5.5 是 $0.10。⚠️ 因此在缓存很重的长运行里，Fable 和 Opus 的差距主要落在未缓存的输入和输出上，那一部分 Fable 每 token 贵一倍。姊妹篇 What a task costs on Opus 5.5 里，一轮缓存读取在 150K 上下文时约 $0.03，在 20K 时约 $0.004。⚠️

由此引出的建议是：主模型越大，主上下文越要精瘦。把贵的模型的上下文留给决策，冗长的阅读交给更便宜的子智能体。

Haiku 5.5 是唯一按提示长度分档计价的模型：不超过 100K token 走低档，超过则按五倍费率。长提示档仍然只有 Sonnet 5.5 每 token 价的四分之一；短提示上，它的输入价是 Sonnet 5.5 的二十分之一。所以它在短提示上最划算。若每次调用都需要很长的提示，就不要只看标价，而要比较「做完一件事」的成本。

把模型混起来用

在自然的断点上切换

提示缓存属于写下它的那个模型。第一次换到新模型时，整段对话都要按缓存写入计价。为了让这一轮小一点：在 Claude Code 里先 /compact，或新开一轮、只带一份短计划；在 API 上，用到目前为止的摘要开启新对话，不要把完整历史原样搬走。

每段 thinking 都会记下是哪个模型写的，而且每个模型只能读一部分其他模型的 thinking。在 Claude API 以及 Google Cloud 上由 Google 托管的 Claude 模型中：Opus 5.5 能读 Sonnet 5.5 和 Haiku 5.5 的；Sonnet 5.5 能读 Haiku 5.5 的；Fable 5.2 能读 Opus 5.5、Sonnet 5.5 和 Haiku 5.5 的。在 Claude API 上，Fable 5.1 能读 Opus 5.5 的。向下换一档会丢掉先前的推理，因为模型从不读取比自己更强的模型写下的 thinking 块；其他方向的切换也可能丢掉。新模型读不了时，API 会丢掉这些块，请求仍会成功，只是新模型不再带上那段推理。从 Fable 5.2 换到任何一个其他一般可用模型，都会丢掉它的推理。细节见 preserved thinking 文档。

把子智能体放在更小的模型上

子智能体有自己的上下文窗口，交回一份摘要，按它所运行的模型计费。在 Claude Code 里，可在子智能体定义中写 model: haiku 或 model: sonnet；未指定时，默认值由环境变量 CLAUDE_CODE_SUBAGENT_MODEL 决定。

原文给了一个日志阅读子智能体的例子。按站点条款，代码示例默认 MIT，下面照录并保留许可说明：

---
name: log-reader
description: Reads test output and logs, and reports each failing case. Use after a test run.
tools: Read, Grep, Glob, Bash
model: haiku
---

Read the logs you're given. For each failure, report the file, the test name and the first error line. Don't edit any files.

代码示例 © Anthropic，按 claude.dev Terms of Use §1 以 MIT License 许可。保存为 .claude/agents/log-reader.md。使用时请保留版权与许可声明。

小模型只做「错了也容易看出来」的事：找文件、跑测试、读日志。改代码和做判断留在主模型。小模型若读错一条搜索结果，主模型就会打开错误的文件，把 token 花在上面。

当前版本的 Claude Code 里，内置 Explore 子智能体跑的是当前会话的模型，而不再总是 Haiku；在 Claude API 上，这个模型最高用到 Opus。若要让探索保持便宜，可自己定义一个也叫 Explore、model: haiku 的子智能体，并用 ANTHROPIC_DEFAULT_HAIKU_MODEL 钉死 haiku 别名指向的模型。

在 Anthropic API 上，haiku 别名现已解析为 Haiku 5.5，需要 Claude Code v2.1.293 或更新版本。在 Amazon Bedrock、Google Cloud、Microsoft Foundry 以及 AWS 上的 Claude Platform，它仍解析为 Haiku 4.5。⚠️ 这是原文在 2026-11-09 的说法，各云厂商随后可能已变，以 model configuration 文档为准。

Claude Code 还有 opusplan 别名：在 plan 模式里用 Opus 做计划，再交给 Sonnet 执行。这会把代码修改放到 Sonnet 上。上面的建议正好相反：改代码留在主模型，小模型只做容易核对的边角工作。把 opusplan 设为默认之前，先在自己的任务上测过。

把难题交给顾问

advisor tool（beta）让一个更快、更便宜的执行模型，在中途向更强的顾问模型请教。大部分 token 按执行模型计费。顾问只在执行模型缺某种能力、并且主动来问的时候才出手；effort 低时，请教也会更少。

可能划算的场景：大多数回合都例行公事的智能体工作。平台的成本指南本身很谨慎：其顾问表里的四种配对，没有一种明显优于执行模型单干；顾问只有在被请教时才帮得上忙。先测量执行模型的请教率，并核对它接受哪些顾问。举例：Sonnet 5.5 执行模型可以请教 Fable 5.2、Opus 5.5、Opus 5 和 Sonnet 5.5；Fable 5.2 执行模型只接受 Fable 5.2 或 Mythos 5.2。

帮助有限的例子：内部编码基准上，Opus 5.5 执行模型开 high、配 Fable 5.1 顾问，得分 90.1%，每次尝试 $2.92。这比 Opus 5.5 单独开 high 高 1.7 分，花费大约是 2.1 倍。作者认为这点增益已接近多次运行之间的噪声，也大约相当于只把 effort 再升一档能买到的东西。⚠️ 内部评测，未复现。

把大宗工作交给更便宜的工人

上面的子智能体，是在主模型保住一条主线的同时处理边角。下面这种模式针对的是大过单个上下文窗口的工作：由顶层模型牵头，把任务拆开，并行交给许多更便宜的工人，再把结果合并回来。原文称，在一份覆盖约 2200 万 token 源代码的内部缺陷搜索基准上，以 Opus 5.5 带领最多 25 个并行的 Sonnet 5.5 工人，成本大约比单独用默认 effort 的 Opus 5.5 低三分之一，得分大致相当。⚠️ 内部评测，未复现。

在 Claude 平台上，Claude Managed Agents 的 multiagent orchestration 提供协调者与一组工人。一条必须依次依赖的步骤链，或本来就装得进一个上下文窗口的工作，不必用它——这时规划和合并的开销会高于节省。何时该把子智能体折回主循环，见 When to fold subagents into your main agent loop。

迁移前先看兼容性

选型主要是能力和成本的问题，但不能假定改一个模型名就万事大吉。原文列出若干迁移前要测的差异：

  • Fable 5.2 把 preserved thinking 扩展到每个 API 账户。 若 Fable 5.2 的某段 thinking 之前的任何内容被改过——包括系统提示、工具或更早的消息——API 会返回 400，除非你选择丢掉受影响的 thinking。经 Claude Code、Claude Agent SDK 或 Claude Managed Agents 组请求，不必改自己的代码；若是自己的代码在改历史，应保持只追加，并在切换前测试。
  • Thinking。 Opus 5.5 和 Fable 5.2 始终思考，关掉 thinking 的请求会报错。Sonnet 5.5 默认思考，between_tools 把思考限制在工具调用之间的空隙。Haiku 5.5 默认思考，在 high 及以下可以关掉。读取响应时都应按 type 区分内容块，因为回复可能以 thinking 块开头。
  • 强制使用工具。 在 Sonnet 5.5、Opus 5.5 和 Fable 5.2 上，tool_choice 为 any 或 tool 会返回 400。应发送 auto，把工具标为 strict: true，并在提示里写清何时使用。
  • 计算机使用。 这四个一般可用模型只通过 computer_toolset_20260801 工具集，在 Claude API 以及 Google Cloud 上由 Google 托管的 Claude 模型中支持计算机使用。
  • 从 Haiku 4.5 迁到 Haiku 5.5。 用 effort 级别替换 budget_tokens；去掉非默认的 temperature、top_p、top_k，否则会 400。消息必须以用户轮次结束，若最后一轮是助手、想让模型接着写，也会 400。
  • 安全回退。 Opus 5.5、Sonnet 5.5 和 Fable 5.2 会跑安全分类器，最常标出网络安全和生物学内容。在 Claude Code 里，被标记的请求可能在更旧的模型上重跑，成绩单里会注明是哪一个。Fable 5.2 沿用 Fable 5.1 的回退模型：被标记的网络安全请求回退到 Opus 4.8，生物学请求回退到 Opus 5。

若同一系统要跑多个模型，就把每条请求按其中最严格的那一档来写：历史只追加，发送 tool_choice: auto 并使用 strict 工具，按 type 读内容块，提示词和工具说明写到连最字面理解的模型也够用。这样升一档或降一档都不必改代码。若路由规则很简单，比如每类步骤固定一个模型，就让代码来选模型，不要再问模型该用谁。

用自己的任务来测

像 SWE-bench Pro、Terminal-Bench 这类已发表的数字，只够帮你选定一个起点。真正决定之前，还是要在自己的任务上测候选组合：

  1. 抽一组真实任务，为每一项写好结果检查，例如测试通过、工单关闭，或正确的行数。
  2. 让每个候选模型跑两到三档 effort，每档单独开一轮，避免共享缓存。从每条响应的 usage 字段记下做完该任务的成本。
  3. 把分数对花费画出来。只有当多模型方案胜过图上每一个单模型点时，才保留它。
  4. 切过去之前，先在一片真实流量上做影子运行。

在 Claude Code 里做快速对照：用 /model 把待办里的同一项任务跑在两个模型上，再比较 /usage 的报告。
