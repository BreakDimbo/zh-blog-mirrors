Data Bot：给每个团队配一位数据科学家

Giving every team a data scientist with Grok Bot

Data Bot 是什么

Data Bot 是 SpaceXSI 数据科学团队在 Grok Bot 里搭的一个 Team Bot（团队共用的 Bot）。它能查公司数据仓库、跑分析，再按提问人习惯的形式交付结果。原文一句话定位：数据团队来“教”它，于是任何团队都能 “get answers the way a data scientist would”（像数据科学家那样得到答案）。

它和个人 Bot 的区别是知识来源：个人 Bot 只能学到主人自己会的东西；Data Bot 用的是数据团队共同维护的一套技能，团队每改进一次技能，所有使用者一起受益。它还可以被拉进 Slack 频道，回答问题，也会主动参与正在进行的工作。

为什么要做：数据团队成了瓶颈

作者说，数据科学团队服务全公司，多年下来积累了对数据的“直觉”：数据该怎么解读、局限在哪。但团队人少，公司长得快，每天有大量问题找上门，很多问题本身不难，却需要专业判断才能答准，数据团队很容易变成瓶颈。

几个月前他们开始试 AI 智能体，目标有两层：给每个人配一位 7×24 小时在线、能调用团队集体知识的“数据科学家”；同时把数据团队自己的工作重心，转向打造和改进这个 AI 队友。

教它：四类技能

要让 Data Bot 像数据团队那样思考，靠的是技能（skills）。原文把技能分成四块：

  • 指标与分析：定义全公司的核心指标（如活跃用户、营收）及其来源表和查询逻辑；排查指标变化时先按细分人群或地区拆解，再查节假日或埋点改动，最后才归因到产品改动。
  • 实验：怎么设计 A/B 测试、做功效分析（power analysis）、检查曝光是否均衡和样本偏差、规划放量、深挖反直觉的结果，以及实验达到统计功效后怎么写结论报告。
  • 图表与看板：可视化的基本规范（趋势用折线、类别比较用横向条形图），加上团队自己的图表主题和样式指南；还能把聊天里的一张图做成 Databricks 或 Hex 看板，供全组使用。
  • 数据工程：编写和评审 dbt 模型的规范、自动化管道告警约定，以及如何为新功能加埋点，让功能一上线就能度量使用情况。

值得注意的是，这四块写的都是团队的做法和口径，不只是“怎么连数据库”。指标定义、归因顺序、出图规范这些平时靠口口相传的经验，被写成了可复用的说明。

共享记忆：经审核才对所有人生效

Data Bot 有共享记忆，能把日常使用中出现的新知识留下来。原文举的例子：记住某条数据管道归哪位同事负责；记住某次关键指标下跌后来查明是某地区放假。下次遇到类似下跌，它会先查节假日日历，再考虑是不是产品改动造成的。

关键设计是审核：作为 Team Bot 的管理者，数据团队可以逐条查看 Data Bot 提议写入记忆的内容，批准或拒绝之后，才会对所有使用者生效。这让“边用边学”不至于把一次错误的结论扩散给全公司。

三类用户怎么用

产品经理：口袋里的数据科学家

PM 关于“用户到底怎么用产品”的问题源源不断，很多超出现有看板的范围。以前要么自己钻数据，要么去找数据团队。原文提到 PM Kevin Niparko 在 Grok Bot 里像给同事发消息一样问 Data Bot，几分钟拿到答案，还能接着追问，不用重开一轮分析；他的说法是 “a data scientist in his pocket”。

作者特别指出“提问成本”的变化：以前哪怕打开看板、或在 Cursor 里开个分析，都有足够的摩擦让人放弃一些问题；现在这些本会被放过的问题也会被问出来。Data Bot 还会适应个人偏好：Kevin 喜欢“一句结论 + 一张图”，它就按这个格式交付。

营销：活动到底带来了什么

邮件平台只统计打开和点击，看不出活动是否达成目标。负责生命周期营销的 Jon Brenner 把 Data Bot 当作随叫随到的分析师：给它一个 Braze 活动 ID，问收件人后来做了什么，它去数据仓库查点击者有没有真正用上相关功能。原文的例子是 The X Subscription 上线时，Braze 自带的转化指标答不了“多少收件人真的换了套餐”，Data Bot 直接查仓库统计了收件人数和换套餐人数。

营收增长：活动对销售的影响

营收增长总监 Katy Abbaszadeh 用 Data Bot 衡量线下活动对销售的影响：活动带来多少销售线索、是否加速了已有交易；还用它每周跟踪目标进度、排查进度放缓的原因，并把结果做成演示用的图表。

从回答问题到整套分析、定时汇报

Data Bot 不止回答单个问题。比如某个 PM 想弄清产品采用率为什么变了，Data Bot 可以自己规划分析、查仓库、排查可能的解释，最后交一份带图的书面报告，或者在 Hex 里搭一个团队能继续用的看板。原文说这类项目以往要和数据科学家来回协作好几轮。

在 Slack 频道里，团队可以把例行汇报交给它：比如盯一个关键指标，按数据团队定好的汇报规范每周发一次更新。它按计划自动运行，把更新直接发到群聊里，同事看到异常可以当场追问或让它深挖。

效果与边界

原文称 Data Bot 在公司内部的使用增长很快，并给出一个估算：上周它处理了约 70 小时、原本会落到数据科学团队头上的工作 ⚠️（发布方自估，未给计算方法）。

作者也写了边界：需要更多判断的复杂分析仍由数据团队自己做，他们也还在摸索 Data Bot 在哪些地方需要更多指导。目标是让同事随时能调用数据团队的专业能力，同时让数据团队把时间留给真正需要他们亲自处理的问题。

对我们的启发

以下是本站的看法，不是原文内容 ⚠️ 推断：

  • 先写口径，再接数据。Data Bot 的价值主要来自“指标定义 + 归因顺序 + 出图规范”这些团队经验，写成技能后人人可用。个人或小团队也可以先从一份“核心指标怎么算、异常先查什么”的技能开始。
  • 记忆要有闸门。“提议—审核—生效”的共享记忆，和个人知识库里“改正沉淀到 rules、原始资料不可改”的思路一致：让知识能积累，也能追溯和纠错。
  • 降低提问成本本身就是产出。原文最有意思的观察是“摩擦让人放弃提问”，Bot 的作用之一是把这些问题重新捞回来。
  • 边界写清楚。原文没有把 Data Bot 说成能替代数据团队，复杂判断仍归人。搭团队 Bot 时，同样值得写明哪些事它不该自己拍板。
