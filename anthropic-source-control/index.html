Redesigning source control at Anthropic

是什么 / 核心观点

  • 是什么：Anthropic 工程博客的一篇长文，讲他们为什么在 5 个月内用自研版本控制系统 Scion 替换掉 monorepo 上的 git，以及 Scion 是怎么设计的。同期上线的还有代码评审工具 Antique、代码搜索、源码 IAM 等。
  • 核心观点 1：写代码不再是瓶颈，瓶颈变成了按人类规模设计的开发基础设施（源码管理、构建、CI）。每日合并数从 2026 年 5 月的约 2,500 涨到 9 月的 30,000 以上。
  • 核心观点 2：git 的强项是去中心化和离线，但智能体和 CI 任务“天生在线”。所以应该反过来设计：服务器负责重计算，客户端做薄，工作副本可有可无，一切靠内容寻址和缓存横向扩展。
  • 核心观点 3：Claude 既造成了这个问题，也是解决它的工具。一个 7 人团队 5 个月完成，基础设施占用缩小到原来的 1/200，检出从“分钟”降到“秒”。工程师的工作重心变成把握设计约束、对 Claude 说“不”。
  • 核心观点 4：Scion 不适合普通团队直接替代 git。但其中的思路，比如完备的服务端 RPC、只按需请求对象的协商协议、能良好组合的 sparse/shallow 功能，可以回馈到 git 生态。

引言：瓶颈换了地方

文章开篇判断：“coding is no longer the bottleneck”（写代码已不再是瓶颈）。Claude 能自主跑研究循环、微优化复杂程序、从零搭服务，于是压力转移到 “developer infrastructure built for human scale”（为人类规模打造的开发者基础设施）上。

数据：2026 年 5 月日均合并约 2,500 个变更，9 月超过 30,000 个。作者认为合并代码的潜在需求 “practically infinite”（几乎无限），每移除一个瓶颈，代码产量都会立刻再涨一截。原文第一张图是 1–9 月每日合并量曲线（查看原图 ↗）。

为此他们造了 Scion，用 5 个月把 monorepo 从 git 完全迁过去，同期还做了评审工具 Antique、代码搜索、源码 IAM，以及管理和落地大量已评审代码的新方法。本文只讲 Scion。作者把它看作一个有意思的案例：Claude 的编码能力既是问题的来源，也是快速造出高质量系统的原因。

不断膨胀的 monorepo

作者先承认自家负载很特殊：Anthropic 用 Claude 写代码的程度远超几乎所有公司，所以总是最早看到人类规模工具在哪里吃不消。短期内多数组织不会遇到这些问题，但用 AI 编码工具的团队迟早会碰到同样的压力点，这也是他们写这篇文章的原因。

git 的设计是去中心化的：每个 clone 都是完整仓库，离线也能 diff、看历史和 blame、检出任意版本。作者明确说，对绝大多数仓库，这就是正确的设计。

但他们的 monorepo 已经超出这个设计空间：

指标数值
main 分支历史近 100 GB
压缩后的工作副本超过 25 GB
CI 每日检出次数约 2,500 万次（不含开发环境、智能体沙箱、研究任务）
朴素拉取时的流量每天超过 600 PB

常规手段他们都试过：浅克隆、稀疏检出、promisor remote，加上内部 git 镜像，以及放在 blob 存储里的仓库快照（seed）。高峰期运维着 数百个内部 git 镜像。这些办法争取到了时间，但合并速率越高越难维持：seed 在两次刷新之间离 main 越来越远；在部分克隆上保证 diff、blame 这类依赖历史的操作正常，也越来越费劲。原文这里配了一张“扩展 git 检出的典型架构”图（查看原图 ↗）。

关键的一步反思：他们和大多数公司一样，其实是把 git 当中心化系统在用，只有一份权威副本；而客户端几乎全是 “online by definition”（天生在线）的智能体和任务。git 最擅长的分布式、离线特性，反而成了扩展的阻碍。于是问题变成：“if we designed source control with the fact that agents are always online in mind from the start, what would it look like?”（如果从一开始就假定智能体永远在线，源码管理该长什么样？）

六条设计原则

作者说明，超大 monorepo 的源码管理有前人经验可借，特别是 Google 的 Piper 和 Meta 的 Sapling。Scion 在下面几条核心原则上和 git 走了不同的路：

  1. 客户端永远在线。git 假定客户端离线、需要全量副本。Scion 的客户端和协议都围绕一个始终可达的服务器设计，数据用到时才拉。
  2. 客户端和服务器不对称。git 的每个客户端都能当完整服务器。在 Scion 里，历史和 blame 查询、创建提交、merge、rebase 都由服务器完成。客户端只做四件事：维护有界的本地对象缓存、把工作副本铺到磁盘、监视文件系统变化、提供顺手的交互界面。原话是 “It can compute very little on its own but… requires much less data locally.”（它自己算不了多少，但本地需要的数据也少得多。）
  3. 完备的源码服务能催生新应用。用 git 时，CI 或工具想知道“这一行谁最后改的”“两个提交什么关系”，要么自己维护本地仓库，要么依赖托管平台的私有 API。Scion 把客户端用到的所有查询都开放成 API，很多任务因此完全不需要本地仓库。自动 bisect、自动 revert 流水线这类内部工具，没有这种廉价的程序化访问，在规模上就跑不起来。
  4. 一切可水平扩展。数百个 git 镜像严重挤占容量，仓库一旦超出镜像的磁盘或内存就无法再扩。Scion 的数据是分布式的，每个组件独立扩展。“there is no fully materialized copy of the repo anywhere, even on the server”（任何地方都没有完整物化的仓库副本，服务器上也没有）。也没有 packfile 的等价物，所以不需要做仓库维护。
  5. 提交要廉价、增量、无锁。提交、rebase、merge 全在服务器上发生，没有“push”这一步，所以每个操作都必须很快。创建提交、更新下游数据结构的成本必须随变更大小增长，而不是随仓库大小增长。Scion 的开发流程也不鼓励用 ref（分支、标签），只保留 main 和发布分支，因为所有服务器都必须达成一致的全局状态是迟早要出问题的扩展瓶颈。
  6. 工作副本可选，天生稀疏。CI 要拿某个提交和它的 merge base 之间的 diff，直接问服务器就行；很多写操作也能跳过检出，全走 API。真要落盘时，协议以稀疏检出（只取请求的目录）和虚拟化检出（读到哪个文件才物化哪个）为核心，客户端只为实际读取的部分付费。

Scion 如何工作：数据结构

作者提到，这些思路也适用于其他源码系统，甚至开发生命周期的其他环节。

changeset（变更集）。Scion 的工作单元是 changeset，也就是预写日志（write-ahead log）里的一条记录。它和 git commit 内容相近，关键区别在于：git commit 指向一棵完整的树，changeset 只存相对第一个父提交改动了哪些文件，以及指向 blob 存储中压缩内容的内容寻址指针。changeset 在服务器端生成，生成后立即全局可见。原文脚注解释，merge 只相对第一个父提交记录是一种风格选择：在 monorepo 的主干开发中，大家只关心主线提交的历史和 blame。原文附有 changeset 结构图（查看原图 ↗）。

这种结构吞吐很高，因为没有 packfile 要接收，不用加锁，不用跨服务器协调，也没有 ref 要移动。Scion 技术上支持 ref，但创建和拉取提交都不涉及它；移动 ref 只是对 Spanner 中单行做一次 compare-and-swap，和创建 changeset 分开进行。

派生数据（derived data）。changeset 只记录“改了什么”，回答不了“这一行谁最后改的”“哪些提交动过这个文件”。为此，Scion 在 changeset 之上构建额外结构：文件 blame、路径历史、提交图的跳表等，统称“派生数据”，全部由一个通用机制计算。每种派生数据都是递归定义的：某个 changeset 上的值，由它各父节点上的值推出。这个机制有三个好处：

  • 新的数据结构能加速某个操作时，可以很方便地加一种派生数据；
  • 每种派生数据都可以选择立即计算还是延后计算，不需要的就不物化；
  • 客户端看不到这些内部结构，所以优化它们不用改客户端。

随着系统发展，他们已经多次新增派生数据类型，例如用于拷贝检测、按路径搜索文件的索引。

扩展 Scion：检出架构

服务器本质上是缓存。一小组 Scion 服务器提供各种 API：取 changeset、算 diff、找 merge base、取 blob。所有数据都是内容寻址的，写入后不再改变，所以任何服务器都能直接缓存，不用和其他服务器核对。服务器因此可以水平扩展，几乎不需要协调，作者形容它们是 “essentially large caches”（本质上就是大缓存），同时还能即时计算派生数据并写回 Spanner。

先做元数据，再做检出。迁移早期，Scion 还没有自己的客户端、仓库格式和协议，只回答祖先关系、blame 这类“元数据”查询。仅此一项，就让 CI 和各种工具不用再维护本地仓库。拉取文件内容、物化工作副本的数据量大得多，需要单独设计。

反过来的协商协议。scn 客户端与 git fetch 的关键区别是：协商时不告诉服务器自己已经有什么，只请求自己想要的树和 blob。客户端从根树开始，检查本地缺哪些树并递归请求，然后对 blob 重复同样的过程。每个请求都指向一个永不改变的具体对象，任何一层缓存都能应答，整体就像传统的分层缓存。没有单个数 GB 的 packfile 响应，所以过程高效且可续传。稀疏检出和虚拟化检出也不用特殊支持，不想要的树不请求就是了。

三层分级。每个节点上运行一个 scion-daemon，同节点的任务通过 socket 共享它的对象存储。daemon 从定期刷新的快照启动，之后只和本区域的 scion-cache 通信。cache 直接从内存流式发送对象，用的就是 daemon 要用的磁盘格式，不用计算客户端缺什么，也不做 delta 压缩。cache 未命中时，才去问权威的 scion-server，后者按需读 Spanner 或云存储。三层响应完全相同的 RPC，客户端不需要知道拓扑。理论上任意两层都能直连，但他们严格强制逐层访问来隔离故障域，避免某个区域的 cache 出故障后把上游 server 压垮、拖垮整个系统。

效果：

  • 每层缓存命中率都在 99% 以上，不需要长期状态，扩容很容易；
  • 按 CPU 和内存计，基础设施占用比原来的 git 镜像体系小 200 倍；
  • CI 和研究任务检出快两个数量级（以秒计，而不是分钟）；仅 CI 就省出 25% 的 CPU 容量；
  • 客户端和缓存都不用做仓库维护，任务的生命周期管理也简单了。

构建 Scion 的收获

Scion 启动时，正好赶上 Claude Mythos Preview 和 Claude Tag 在内部可用。作者说这两者 “simultaneously amplified the need for Scion and meaningfully accelerated how quickly we could build it”（既放大了对 Scion 的需求，也显著加快了构建速度）。

一个例子：git→Scion 摄取流水线的第一版原型基本是手写的，团队自认还不错。后来拿到 Mythos Preview 的早期内部快照，让它整体重写，没给任何额外指示，结果内存少用 20 倍、速度快 4 倍，摄取顺序和数据结构上的隐含不变量也都保住了。原文配图是 Scion 和 Antique 代码库每周合并量的曲线（查看原图 ↗）。

接下来是六条“构建智能体规模软件”的经验：

  1. 小团队快速开发会越来越常见。7 个人做出了 Scion、Antique，外加半打相关系统，5 个月完成全部迁移，同期每日合并量涨了 10 倍。放在过去，这需要一家公司投入多得多的工程师，花好几年迭代迁移。
  2. 工程师价值不减，但工作内容变了。参与项目的每位工程师都认为 Claude 写代码比自己强。但跨系统的整体理解、设计层面的权衡、要解决什么问题、要达到什么规模，仍然由人来把握。作者说 “the role of the engineers was to tell Claude ‘no.’”（工程师的角色常常是对 Claude 说“不”）。例子有两个：
    • 迁移中有好几个系统想线性扫描提交日志来暴力查“某变更何时合入 main”，而正确做法是直接问代码评审工具。这类做法违反了核心约束，只是在迎合本不该存在的模式。
    • 对抗式评审（adversarial review）总体非常有效，但可能“目光短浅”：有一次评审对另一个内部服务过度不信任，导致 Claude 加了大量多余的校验和复杂度，需要资深工程师出面纠正这种针对假想风险的过度设计。
    现在团队仍然评审每个变更，但看的是变更意图，不再逐行读代码。
  3. 优化和质量都大幅提升。Claude 写代码量大、速度快，Scion 因此成了他们做过的测试最充分、防御最完善的代码库之一：为所有非平凡的基础设施和源码交互都写了封闭仿真，还有模糊测试和精细限流。Claude 还“顺手”发现了重大优化，比如祖先查询漏用了一个索引。这种问题专家要花几天到几周才能分析调优出来，“and then did it all again the next day”（而它第二天又来一次）。原文附有性能提升图（查看原图 ↗）。
  4. 为 monorepo 安全打下基础。Scion 从一开始就考虑了安全和合规：支持仓库级的丰富访问控制，也支持目录级权限，在保护最敏感代码的同时保留 monorepo 的好处。评审工具能对审批表达语义约束，比如区分“只改注释”和“敏感逻辑改动”，让人类评审把精力放在最关键的变更上。
  5. 运维可以做到新的水平。团队大量使用 Claude Tag，在 Slack 里给每个组件建一个频道，让一个 Claude 偏执地只盯这一个组件的健康状况，称为 “superfans”（超级粉丝），如 scion-daemon 超级粉丝、scion-cache 超级粉丝、Antique 合并队列超级粉丝。它们能读遥测和日志，像一位“除了刷图表找异常之外无事可做的资深工程师”。传统告警照样保留，但超级粉丝能发现细微而新颖的问题，相比之下告警显得很“一维”。
  6. 彻底重新审视既有认知。正规的合并队列在智能体规模下不太说得通：测试还在跑，就已经有成百上千个变更合进来了，CI 还意味着什么？他们没能有效复刻业界“合并队列加全局仓库锁”的标准做法，转而投入合并后、部署前的自动化测试。代价是并发变更可能冲突，但 Claude 修冲突通常比人发现冲突还快。

回馈更广泛的生态

  • Scion 只是应对 AI 智能体带来的扩展问题的答案之一，“by no means a suitable replacement for git for general use”（绝不是通用场景下 git 的替代品）。它只对真正巨大的 monorepo 有意义：要么有数万名工程师，要么有成群的智能体在大量写代码。另外，Anthropic 内部花 token 的能力远超其他企业愿意承受的程度，这既是为了自身开发，也是为了测试 Claude 的能力。
  • Scion 很难开放给外部使用：它和 git 差异太大，采用它要迁移整条开发链路，还要配套自己的评审、搜索和 CI。这些内部组件高度定制，做一个“讨好所有人”的公开版本，大概也没什么用。
  • 他们预计这类问题会在未来 6–12 个月变得普遍。与其让每家公司独自摸索，不如把思路分享出来，让大家在不脱离 git 模型的前提下用上 Scion 最成功的部分。具体方向有四个：git 服务器不必和客户端同构，已有能大幅提升扩展性的新型服务器架构；git 平台可以提供 Scion 那样的完备服务端 RPC，最好跨代码托管平台标准化，让 git 客户端学会调用；协商协议不必保持现在的样子；sparse 和 shallow 等功能应该能良好组合。
  • 最后，作者致敬 git 社区近二十年来为数百万开发者扩展这个平台，表示希望和 GitHub、GitLab 及开源社区合作。结尾一句是 “We’re all in it together as the software development lifecycle intersects with the AI exponential.”（软件开发生命周期正与 AI 指数曲线交汇，我们同舟共济。）

对我们的启发

  • 按“智能体在线”重新审视工具链：如果客户端主要是智能体和 CI，很多“本地全量”的假设就可以放弃，把查询做成服务（blame、merge base、diff 走 API），工具也就不用再 clone。
  • 内容寻址加分层缓存是扩展的利器：不可变对象可以随意缓存；协商只请求“我要什么”，不声明“我有什么”，天然支持续传、稀疏和虚拟化。
  • 派生数据统一递归计算：主数据保持极简（只记差异），索引用通用机制派生，可以选择立即或延后计算，新增索引也不会影响客户端。这个模式适用于很多日志型系统。
  • Harness 比代码更重要：人的价值在于守住约束、对过度设计说“不”、评审意图而不是逐行；对抗式评审也需要人来校准。
  • 用智能体做运维“超级粉丝”：一个组件配一个专职盯盘的智能体，作为传统告警的补充。
  • 流程也要按智能体规模重新设计：合并队列加全局锁扛不住时，可以接受冲突、转向合并后测试，再靠智能体快速修复。前提是有足够的部署前防线。
  • 保持清醒：文中多数数字来自 Anthropic 自身独特的规模和 token 预算，普通团队更现实的做法，是留意 git 托管平台未来在服务端 RPC 和协议上的改进。
