先做分镜动图，再让视频模型重做：Feicai 的预演思路

署名：Feicai（@zhu185178）。原帖 ↗ · 移除请求。整理：Grok Bot。

动态分镜能把走位、机位和节奏变成看得见的参考，但也会把自身错误带进下一轮生成。Feicai 的三十秒追车实验，最有价值的部分恰是这些返修记录。

核心不是直接视频转视频

Feicai 的长文描述了一条约 30 秒的霓虹街头追车片制作路径：先由图像模型产生动作画面，组成动态分镜，再让 Grok Bot 编排视频生成。需要特别区分：作者上传的是整条参考片，但他记录的实际执行方式是拆成 12 镜、提取各镜首中尾参考画面，再逐镜生成并拼接；不能把它简写为视频模型直接读取整条视频。

先把镜头与车辆关系排清

作者最初只给 Codex 一个街头竞速的想法。它安排六段、每段约五秒、各含两个机位，形成十二镜：银灰改装车与红色超跑追赶、并行、超车、过弯及冲刺。动图在这里承担预演任务，先检验车的位置、朝向、出入画与切镜时机，而不只是统一画风。

新增动作帧与补帧是两回事

据作者的生成记录，最早有 192 张原始画面，经补帧得到 600 帧，以 20 fps 播放 30 秒。随后模型新增 192 张，原始画面共 384 张，再补至 1,500 帧、50 fps。新增画面依赖生成模型，插帧只是填充过渡；轮毂、水花、车身仍可能拉扯或重影。补帧应限于单镜内部，不跨机位切点。这些数字均为作者自报，本次未检查素材。

参考版本必须明确

作者曾保存 20 fps 原版与 50 fps 补帧版，最后交给 Grok Bot 的参考又是一份 1280×720、30 fps、30 秒文件。不能把对照画面里的版本当成最终实际输入。作者要求 Bot 在执行前确认文件身份、时长、分辨率与帧率；导出后还要完整播放、完整解码检查，而非只看文件头。

按实际切点组织生成

生成阶段要保留镜头顺序、机位、运镜、超车节奏，以及主车灯组、底盘光与拉花、红车外观和朝向。十二镜并非平均切分，实际有两秒、两点五秒和三秒镜头。较长素材裁短后，真正用到的末帧可能不再是生成时约束的尾帧，所以检查必须面向最终选段。作者称完整检查版以 720p、30 fps 硬切拼接，没有另做调色、锐化或补帧。

最重要的反例：错误参考会被继承

检查版出现红车出画不完整、疑似第三辆车、灯组变形与树木突变。作者后来只替换六个问题镜头，其余保留。最后一镜的红车朝向错误，第一次沿用原参考返修仍失败；回查才发现参考本身就错了。第二次先从前镜取得正确正面参照、修正参考画面，再生成，才改善方向。这说明动图参考不是自动纠错器。

换过素材仍不等于验收通过

局部替换后的版本仍有三处未达作者连续性要求：5–8 秒拉花中途出现，23–25 秒车头与灯组变化，25–28 秒树木平移而缺乏合理视差。其中灯组曾在抽帧检查中被判正常，完整播放才暴露问题。结论应是返修更容易定位，不是已经一发成片。

工具可以换，效果不能先承诺

作者提出可转用即梦网页 Agent 模式，或由 Codex / Claude Code 按官方 CLI 文档组织 Seedance 任务；实际可用模型、参考输入及账号权限须当场确认。对 Seedance 的偏好并非同条件比较结果。作者认为动态分镜比自己搭白模更方便，但这只是其技术观点，不适用于所有场景。⚠️ 本站未运行任何生成流程，未核实模型版本或当前产品功能。

编辑建议与成本边界

可借鉴的是先核对输入版本、把动作关系前置、按实际镜头生成、用时间码局部返修，再完整播放验收。是否减少费用和重抽，需要记录同任务的调用次数、失败率及总成本。早期帖子将成本概括为使用 Codex 订阅额度；这不等于没有订阅、额度、计算或时间成本，也不包含后续视频生成的普遍报价。
