全文中译：《我如何与 Agent 一起工作》

英文原题 How I work with Agents。以下为作者本人 X Article 的完整中文翻译；原文中个别笔误（如 “now How”“featuer”“inicident”“ambitous”）按作者本意译出。

……截至 2026 年 10 月。

  1. 用最新、最强的模型。别的都可能是在浪费时间。一个模型如果有 10% 的时候是错的，你并不知道是哪 10%，于是只能多试几次。你什么时候会真心想雇一个便宜 50%、却会随机笨 20% 的通才？现在谁还在用 Opus 4.5？就是这个意思。

  2. 别再担心“垃圾代码”（slop）越积越多。“它会把你的代码库变成一团没法维护的烂摊子。”也许六个月前是这样。现在？我不确定它还会添加垃圾。就算会，我也不确定结果就没法维护。

  3. 提示“要什么”，而不是“怎么做”。描述你想要的结果（What），而不是你会怎么去做（How）。这样往往效果更好。“把字节码编译器和虚拟机做得尽可能快。不到快 2 倍不许停。”“最终应该是这样工作的：……”

  4. 让整个软件开发生命周期（SDLC）对 Agent 清晰可见。是什么让幻觉停下来的？工具调用。工具让 Agent 能触碰我们的现实。Agent 看不见的东西，它就会编出来。所以，让它端到端地运行自己构建的东西，让它读生产日志、部署、盯着发布过程、切版本、打开功能开关、分诊 bug 报告、给客户发邮件。凡是你能看到的，Agent 也应该能看到。

  5. 给它覆盖 SDLC 的工具。我们有自定义插件，用来处理 bug 报告、给用户发邮件、回答“我们的系统健康吗？”以及授予功能开关。

  6. 评估 Agent 层面的知识。知识会在代码库里不断堆积：AGENTS.md 文件、skills、脚本、文档。可 Agent 真的会用它们吗？派出五个“盲测” Agent，分对照组和实验组，答案自然揭晓。Agent 非常、非常擅长跑实验。

  7. 本地开发现在感觉很别扭。每个 Agent 都应该能安装、运行它完成任务所需的任何东西。在远程机器上这很容易，在本地开发里就很别扭。当你想让 Agent 端到端测试时，在本地很难不撞上资源冲突。

  8. 别跟 Agent 一来一回地迭代，让它自己造迭代用的工具。不要“试试这个……啊不对，试试那个”。而是：“生成 20 个变体，再做一个小页面让我组合、测试它们。”这不仅适用于解空间，也适用于问题空间：“给我 4 个关于它为什么慢的猜想，然后把四个都验证一遍。”

  9. 索要无可辩驳的证据。最大的改变游戏规则的一条。Agent 非常擅长拿出证据：端到端的演示流程、演示视频、改动前后的数字。你得逐步建立信任，并培养出对这件事的直觉。在你的 AGENTS.md 里写上“这不算证据”。

  10. 别等你的 Agent，让它们等你。如果你在纠结首 token 延迟（TTFT），你多半做错了什么。拥抱异步。给它们更大的任务，更有野心一点。批量处理，而不是来回拉扯。

  11. 自动化 / 定时任务 / 唤醒 / 心跳是杀手级功能。我之前没意识到，直到它被关掉才发现自己多么想念它。我一直在用。“两小时后去看看日志。”“上线了告诉我。”“每天早上 9 点检查一次。”

  12. 别再手动管理上下文。你花在琢磨“它现在用的是 30 万还是 38 万 token？”上的每一个念头都是浪费时间。压缩（compaction）效果好得惊人。别手动管理上下文。一个线程 = 一个任务。有的线程 46 条消息，有的 3,714 条。

  13. 线程就是公司的记忆。（在 Amp 里）“我们当初为什么这么做？”团队用 Amp 越多，知识就成倍积累。线程与 git 提交相关联。改变游戏规则。避免重复劳动。

  14. 别让 Agent 替你写给人看的东西。例外：调试步骤、事故报告、某些文档——那些机械性的、对面是谁并不那么要紧的内容。

  15. 只审查高爆炸半径的代码。有不到 5 个核心文件——这些我会审。数据库迁移，审。闭包还是类、更漂亮的类型、变量命名，甚至重复代码：我已经不在乎了。它能跑吗？我能在“架构图里的箭头”这个层面理解它吗？Agent 端到端测过了吗？一个月后我还能改它吗？如果都是“是”，也许我会去审代码。

作者在评论区的补充

以下为 Thorsten Ball 本人在该帖回复中的说法（中译，按主题整理）。

  • “这不算证据”是什么意思？“你需要校准 Agent 对什么才算真实证据的认识。例：本地内存数据库不能作为生产环境性能的证据，应该用真正的生产金丝雀。当然这是夸张的例子，大多数模型不会犯这么明显的错，但确实有些会。”
  • 上下文与成本：被问到用 1M 上下文模型是否还手动压缩，他说“从来不去想，就让 Amp 自己压缩”；“现在有压缩了，它会在进入奇怪状态之前压缩。不，上下文管理已经不是问题了。”至于成本：“我真的不在乎成本。在 Amp，我们把搞清楚未来往哪走当作自己的工作（我们毕竟是 Amp Frontier Corporation），盯着 token 计量表帮不上忙。”
  • 为什么“记录 Agent 每一步再复查”是浪费时间：“跟踪 Agent 到底做了什么、再检查它做得对不对——因为你不信任它——这才是浪费时间，如果你能用更好的模型的话。”
  • 本地资源冲突（端口、同一个 Postgres）：“对。所以才有 orbs。”——指 Amp 的远程机器 Orbs（见下）。iOS/Android 模拟器目前“用 runner 跑，但有新东西要来”。
  • 新模型多快换：“尽快试，这是我的工作。”
  • 自动化线程被淹没怎么办：“我把它们 snooze 掉😃——‘暂停到下次回复’，只有有事时它们才会醒。”另一位用户说应该让自动化主动 ping 自己，他回“对”。
  • 线程作为公司记忆的异议（有人故意不在提交里链接 Agent 线程）：“嗯，这是一家公司里用好多种 Agent 的坏处 :)”
  • “看得见部署”与“能动生产”应是不同权限：他回：“对，本来也不是同一个权限啊？”
  • 有人建议 UI 里加一个“证明它”按钮：“正在做相关的东西 :)”

背景：Amp 与 Orbs

Thorsten Ball 在 Amp（编码 Agent 产品）工作，文中“线程与 git 提交关联”“自动化 / 唤醒”“远程机器”都对应 Amp 的功能。按 Amp 文档，Orbs 是 Amp 为每个线程创建的远程隔离机器：带着你的代码、插件和开发工具，Agent 可在里面装依赖、跑应用、开浏览器做端到端测试；空闲后自动休眠、休眠不计费，下次发消息时带着文件和服务状态醒来（CLI：amp -ox "提示词"）。这正是第 7 条“本地开发很别扭”的解法。

读后注记

  • 这是一份带立场的个人经验，而非实验结论：作者明说不在乎 token 成本、是 Agent 产品从业者，且很多条（压缩、线程即记忆、远程机器）依赖 Amp 的具体能力。换成按量付费的个人或别的工具，“别管上下文”“用最贵的模型”需要自己权衡。
  • “不再审查大部分代码”的前提是第 4、9 条：Agent 能端到端运行和验证，并且你校准过它对“证据”的标准；关键文件、数据库迁移仍要人审。
  • “Opus 4.5”是作者举的过时模型例子，意在“别用上一代模型”，并非对具体模型的评测。
