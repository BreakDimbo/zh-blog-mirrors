1. Made by mechanical means（2026-09-27）

原文 ↗ · 约 13 分钟 · 标签 claude、Workflow

大家问他最多的不是功能需求，而是“你自己怎么用 Claude”。这篇用重做个人主页做示范：不碰代码、不在本地运行、不开 GitHub、也没用传统意义上的 Claude Code，全程 Opus 5.5。

  • 结构：一个 Claude Project 负责整件事，下面分出约 60 个线程，很多并行。每个线程有自己的云端电脑，自己装 Blender、FFmpeg、Playwright，用无头浏览器截图自查，再发布私有预览页。所有线程共享一个文件夹和一份记忆；Claude 会把他做过的决定写进记忆，新线程自动遵守。他说现在和 Claude 谈的“更多是目标，而不是怎么做”。
  • 发散：像对设计团队一样丢一堆灵感（90 年代锐舞海报、电影、广告），10 个线程并行出方向，喜欢的就“再给五个变体”，共 25 个草案。Claude 提出“每件作品是一盘录像带”，和他想要的“90 年代德国电影里记者的房间”合在一起；第二稿在第一次需求后 39 分钟就到了，最终迭代约 60 轮。
  • 房间：约 3000 行 Python 把 Blender 当库来驱动（录像带、90 年代书桌、米色老 PC、身后半个房间各一个脚本）；纹理也是程序噪声。为了柔和的反弹光，用 Cycles 路径追踪把光照烘焙进贴图，电视光单独一层，由当前录像带的颜色染色。窗外是一张 CC BY 照片，用 Depth Anything V2 生成 50 KB 深度图做视差和火车遮挡。
  • 内容：仿拍 Herzog 纪录片里“虚无主义企鹅”的 CGI 版（逐镜头跟踪机位，渲染 2787 帧），再加上公司旗帜等梗；三首配乐由 Claude 先写谱、再写合成器，用 Python 合成。他只给“Rick Rubin 式”的反馈：喜欢 / 再少一点兴奋。
  • 质量：“I’m not reading the code.”（我不读代码。）他用当工程经理的办法保证质量：严格流程与测量，加上专门找茬的对抗式 QA 线程（写了约 3000 行问题记录，协调线程把问题派回负责的线程）。“A single Claude thread doesn’t write perfect code, a fleet of Claudes holding each other accountable meet my bar.”（单个线程写不出完美代码，互相问责的一群 Claude 能达到我的标准。）
  • 性能：“Models are very good at hillclimbing.” 给线程定帧率、draw call 等目标；用多角度截图逐像素比对，确认提速不是靠降画质换来的。
  • 结尾：他承认会有人觉得没学过 3D 的人不该自称做 3D。他引了波德莱尔 1859 年对摄影进入沙龙的刻薄评论，标题“机械手段制成”就出自这里。

2. How to be more ambitious: A tutorial for humans with models（2026-10-13）

原文 ↗ · 本站完整导读：如何更有野心（导读）

上一篇讲“怎么做”，这篇讲“敢想多大”。他把用 AI 的野心分成四维：速度（略过）、高度（问“目标之后的目标”，例如从修一个崩溃变成保持零崩溃，并改造工作流让模型能拿到崩溃报告、自己复现验证）、深度（坚持顶尖工具、定离谱目标、让模型对抗式复核假设、产生新知识、找外部裁判）、广度（把名词换成动词，组一支“劫案团队”，但不要变成角色扮演）。根因是心理学的自我效能感：限制我们的往往是相信什么可能。

3. Things people get wrong about Electron（2025-01-21）

原文 ↗ · 约 5 分钟

维护 Electron 十年后，他第一次系统写下“为什么用 Web 技术写界面、为什么要捆绑 Chromium”（另见 Electron 官网的 Why Electron 文档），并逐条反驳网上的误解：

  • “JS 对抗原生”：Electron 的本意是混搭，Web UI 可以配任意多的 C++/Objective-C/Rust，1Password 的主体就是 Rust。他为此做了 SwiftUI、GTK、Win32 版的示例仓库。
  • “Web 应用都不好”：市场不这么看；NASA 任务控制、彭博终端、SpaceX 龙飞船的界面都用 Web 技术。
  • “系统 WebView 更快”：Slack 早期用 MacGap（系统 WebView），用户反而觉得比 Chrome 慢；他没见过证明系统 WebView 更快的数据。捆绑引擎的首要理由其实是让开发者自己掌控稳定性、安全性和可靠性，而不是性能。
  • “包体太大”：Electron 应用多在 100–300 MB，但用户实际并不在乎，对比一小时 4K Netflix 约 7 GB。

结尾呼应 2018 年的《Defeating Electron》：“Electron isn’t here to compete with anyone.” 谁做出更好的平台，维护者会握手道谢。

4. Adventures in Measuring JavaScript（2023-11-08）

原文 ↗ · 约 7 分钟

一篇诚实的失败记录（写于 Notion 时期）。目标：像包体积那样，每个 PR 都告诉开发者“你让 JS 的 CPU 开销变大还是变小了”。计时行不通：约 15 MB 的 JS，本地多次运行的变异系数约 30%，上云更差。开发者凭直觉也看不出来，比如 VS Code 曾因 CSS 动画光标吃掉 20% CPU。

他改数 CPU 指令数：在物理机 Linux（含 WSL2）上用 perf，加上 Chrome 曾有、2022 年被移除的线程指令计数（只能用 Chrome 101）。小样本的变异系数从计时的约 5% 降到 0.0022%。但它最后没落地：异步工作（fetch、setTimeout）不计入；测的代码越多，GC 等噪声越大，整个应用启动的 CV 又涨到 15% 以上；依赖旧版 Chrome；只能跑在物理机上，进不了云端 CI。结论原话：“We still don’t know how to tell developers when their JavaScript got a little better or worse.”

5. The Fanciest eCards（2025-02-28）

原文 ↗ · 约 4 分钟 · 标签 management

从 Stripe 时期的经理 Jeff Chan 那里学来的习惯：同事周年、生日时，不用 Kudoboard，而是收集大家的祝福，做一个专门为这个人定制的“过度工程”网站，比如给前 Gmail 负责人做的仿 Gmail 界面，以及他自己做的“Buch Fashion Week”“MajaBnb”。他推荐给工程经理的两点好处：一是真正“看见”这个人，避免公司式庆祝的尴尬；二是借机写代码、试新框架和托管服务。时间从哪来？他引了费曼黑板上的 “What I cannot create, I do not understand”，意思是保持动手本来就是他的硬性要求，贺卡只是把两件本来就要做的事合在一起。

反复出现的主题

  • Web 技术做桌面 / 跨平台。从 2014 年的 node-webkit 到 Electron、Fiddle、windows95，再到他在 Slack、Notion、Anthropic 负责的桌面客户端，十几年一条主线。
  • 开发者体验与“让东西能跑起来”。微软时期大量“一键部署到 Azure”“让 npm 在 Windows 上能用”的文章；后来是代码签名、崩溃调试、贡献者培训。
  • 测量优先于直觉。从 JS 指令计数实验，到用像素差验证性能提升、给线程设帧率目标，他一直在找“可测的裁判”。
  • 工程经理的视角。不逐行审查也能保证质量：靠流程、测量和对抗者。这套办法后来直接搬去管理一群 Claude。
  • 好玩的东西也值得认真做。Clippy、复古模拟器、定制贺卡、3D 房间主页。他把“有趣”当作学新技术的入口。
  • 2026 年转向“带着模型工作”。最新两篇都在讲：目标比做法重要，大胆提要求，用一群模型互相检查。

对我们的启发

  • 把“一个助手”换成“一个负责人 + 一群线程”。项目级共享文件夹和记忆、每个线程有自己的电脑、每轮都发可点的预览页，这比在一个对话里反复改更接近真实团队。本库的翻译/上站流水线也可以这样拆。
  • 质量靠机制，不靠通读。对抗式 QA 线程、问题派回负责人、多轮收敛，和 Claude Code 团队的代码评审是同一思路；规模再上去，就会碰到 Scion 讲的基础设施瓶颈。
  • 先找到可靠的裁判，再让模型爬坡。JS 指令计数那篇说明，测量本身可能比优化更难。给智能体定目标前，先确认指标稳定、能防作弊（比如用像素差防止拿画质换速度）。可参考本库的 flameox。
  • “不会”不再是不做的理由。他不会 Blender、不懂作曲，靠描述加反馈做成了 3D 场景和配乐。代码驱动 Blender、代码合成音乐，和 Huashu-motion、小王子 3D 等页的做法相通。
  • 野心是可以练的。配合《如何更有野心》读：每次布置任务前，先问一句“目标之后的目标是什么”。
  • 个人网站可以是作品本身。可以和本库的个人网站画廊对照着看。
