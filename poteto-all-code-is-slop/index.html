演讲导读

下面按官方演讲页的结构整理。官方页有一篇编辑写的导读，并附 441 段机转文字稿，页面写明「识别错误仍在」。事实以官方导读、YouTube 简介和作者自己的帖子为准。引语都很短。

YouTube 简介里的章节是：把 slop 变成金子；信任金字塔与代码库质量；Dune 与可执行的架构；用 lint 规则代替注释；运行时验证与功能地图；形式验证与界面测试；把 token 花在验证上；11,000 个 PR 与 0.5% 的回退率；先打地基，再谈软件工厂。

开场：数字是结果，题目是信任

官方导读的第一句是：「智能体再犯同一个错时，人很容易再往 AGENTS.md 里加一条警告。Lauren Tan 希望纠正落到更难被忽略的地方：代码库、接口，或一次可执行的检查。」

她从「投入数月改进智能体周围的环境之后，合入了几千个 PR」讲起。官方页写，出货量是惹眼的结果，真正的题目是信任：怎样在增加生成代码的同时，不让人必须事后去抓的缺陷一起变多。

把最强的约束放进代码

她用一座信任金字塔来说明纠正应该往哪移动：代码库设计和静态分析（接口、架构、重构、lint、类型、测试）排在书面说明前面；验证用来提供关于行为的证据；写下来的规则，留给那些还不能被直接编码的判断。

代码库本身也是智能体最大的输入之一。留在仓库里的权宜之计，会变成下一次改动的样板；过时的写法看上去像「这里就是这么做的」，便会扩散。官方页转述了花园的比喻：以前 PR 一次只有几个，评审还能看清新长出来的东西；当成百上千个智能体不断送出改动，周围的结构就比逐一检查更要紧。清理旧例子，是为了改善以后的输出，而不只是偿还旧债。

消灭一类错误，而不是永远评审它

例子是内部的桌面客户端框架 Dune，约束来自做 Electron 应用的经验。官方页写到两点。

其一，团队把 React 的 useEffect 限制在选定的框架内部，而不是要求每个智能体都完美使用它。框架提供受支持的路径，检查会拒绝不合适的替代。这是本地的架构选择，并不是说这个 hook 在所有地方都不该用。

其二，主进程的代码不该进到 renderer 里。他们用 electron-main 和 electron-renderer 目录把边界写进名字，再用依赖分析和 lint 禁止跨错边界的导入。目录说明设计，可执行的检查负责执行。一类无效改动被机械拒绝之后，评审就不必在每个 PR 里重新发现它。

注释可能把你想删掉的权宜之计保存下来

一个不那么显而易见的失败是：智能体写下解释，给快速补丁找理由。官方页举的例子是，用命令式定时器去修补命令式与声明式代码之间的结构错位，然后再用注释说明每处权宜为什么必要。下一次，这段说明会让权宜看起来像是有意为之，等于一张许可证。它也不会像编译错误那样，逼着什么东西必须改掉。

她在自己的产品里对注释采取了故意收紧的政策。官方页把可迁移的教训写得比「到处禁止文档」更窄：解释一个已知的坏模式，并不能阻止它再出现。她更希望看到的是一条有帮助的 lint 错误，指向真正的修法；或者让错误的操作在接口上根本做不出来。于是纠正时可以先问：这件事能不能变成一次检查？在加检查之前，能不能用更好的设计，把这个无效选项取消掉？

评审行为和证据，而不只是 diff

能写出来的代码被拦住之后，剩下的要证明它做对了。官方页写，她会看录像、截图、图示和形式验证的结果。

运行时验证从很具体的地方开始：让智能体自己跑起应用，并使用调试工具。功能地图（feature map）用用户的语言给应用命名，这样「改一下侧栏」不必靠智能体去猜指的是哪个控件。可复用的命令行工具和驱动程序，给智能体一条稳定的操作路径，也给团队留下可维护、可测试的东西。

他们也在试验模型检查、为选定算法做证明，以及基于性质的界面测试。她把这些当成额外的一层，而不是银弹。状态图能让评审看到用户可见的状态有哪些、哪些转换被允许；一张成功状态的截图做不到这一点。她的经济论点是：这些技术从前往往因为手工编写和维护太贵而用得少；智能体把成本压下来之后，就可以在更多产品上做更深的验证。验证并没有消失，只是预算更多地花到了这里。

先把内循环做好，再自动化外循环

官方页转述：她的团队在前一个月合入了大约 11,000 个 PR，相对回退率大约 0.5%，若干客户端性能指标也有改善。这些是团队自报的结果，不是「合并量一上去，任何仓库都会变好」的受控证明 ⚠️。结合她会前的说明，这张 PR 图统计的是所有合入 Grok Bot 的 PR，不是她一个人的。

真正可带走的是顺序：先改善智能体学习的代码；让约束可执行；给智能体一种有力的方式去测试行为；然后再扩大反复调用它们的自动化。临近结尾，她提到一套发布例程：启动一个项目去 fuzz 应用，为发现的缺陷开出修复，并且可以自动合并。这种自主性，建立在前面已经搭好的环境上。如果内循环不可靠，再给它加外循环，只会生产更多不可靠的工作。

官方导读的收束是：工厂并不能靠跑得更快，去挽救一套坏掉的流程。在她的讲法里，工厂之所以成为可能，是因为反复出现的错误已经被设计掉、被自动拒绝，或在人再次发现它们之前，就被验证暴露出来。

和先前那场 2,500 个 PR 分享的关系

2026 年 9 月，她曾把原定 Cursor Compile 伦敦场的分享发到 X 上，标题是「上个月我怎么往生产环境发了 2,500 个 PR」。本站已有导读：一个月 2,500 个 PR。两场不是同一段录像，但主线是连贯的：信任金字塔、Dune、用检查代替口头纠正、功能地图，以及先打地基再加快自动化。这一场把数字更新到了团队一个月约 11,000 个 PR，并把形式验证、状态图和基于性质的界面测试直接放进了演讲；也更明确地限制了 useEffect 的使用范围，以及注释可能怎样把权宜之计保存下来。
