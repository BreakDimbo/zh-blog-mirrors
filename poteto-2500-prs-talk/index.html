视频内容解读

这一节按演讲的顺序整理。主要依据是 Remy 在 redreamality.com 发的长篇复述（2026-10-05，逐段转述，没有公开许可，所以这里只做中文概括，引语很短），加上 Gene Gi 的笔记（2026-09-22），以及作者本人之后在 X 上发的两条帖子，其中一条附了演讲里的幻灯片。本站没有看视频，也没有逐句核对，各条都注明了出处。

1. 开场：数字不是重点，信任才是

  • 视频里她说的是上个月合并了大约 2,000 个 PR 进生产，比帖子标题的 2,500 少了 500。她也说这个数字从来不是她的目标。〔Remy〕
  • 她的论点：产出来自信任，而不是多开智能体。信任的意思是，没有人盯着的时候，智能体交出的活依然够格。〔Remy〕
  • 她不喜欢“软件工厂”这个说法，更愿意比作米其林后厨：不是流水线批量复制，而是手艺活。工程师不再亲手切菜，但端上桌的每道菜仍然由自己负责；要操心的是谁站哪个灶台、用什么刀具、受过什么训练、备菜和主厨怎么配比。〔Remy；Matt Pocock 访谈摘要〕

2. 起点：半年前在 Cursor 的“人肉性能分析”

  • 大约半年前她刚加入 Cursor（当时还没并入 SpaceX AI），接手新 agents window 的性能问题。之所以找她，是因为她以前在 React 团队。〔Remy〕
  • PR 像墙一样不断涌进来，她判断不了性能有没有退化，只能整天开着 Chrome DevTools 抓 trace、拍 heap snapshot。手工到让人烦躁，于是她开始想：能不能让智能体自己启动应用、抓 trace、读懂 trace、找到热点，一步步把性能“爬山”往上推？这就是验证类 Skill的起点。〔Remy〕
  • 她当时的想法是：“我就是瓶颈”，得把工程师脑子里的知识交给智能体。〔Remy〕

3. 没有信任，开 100 个云端智能体只会产出垃圾

  • 一开始她同时只敢盯 1 到 5 个对话，每个都要不停纠偏。人一走开，智能体要么停着不动，要么做错。她认为这是最难走出来的阶段，因为看不到出口。〔Remy〕
  • 在这个阶段开 100 个子智能体或云端智能体，得到的只会是一堆垃圾 PR、回归和 bug。所以真正的问题不是“还能多开几个”，而是“做到什么程度才敢不盯着”。〔Remy〕

4. 核心框架：每次纠正，先问最强的那一层能不能兜住

她把“纠正放在哪里”从强到弱分了几层，顺序本身就是论点：层级越高，越不依赖某个对话里有人记得去读某段提示词。作者 10 月 16 日的帖子说这张图“按价值排序”，并称它为一个倒金字塔：大部分力气应该花在顶层，底层花得最少。〔作者 X 帖 2110603122745970914、2111133080526495985〕

  1. 代码库与架构：从类别上让坏模式写不出来。代码库就是智能体的记忆，它会照着已有代码继续写；一个小 workaround 或者解释它的注释，几天内就会被复制成事实标准，她把这比作病毒，或者花园里的杂草。改数据结构、改做法，比每次口头纠正同一个错误更有效。〔Remy〕
  2. 静态分析：lint、编译器、测试、CI，作者后来的帖子还把 TLA+ 这类形式验证也放进这一层。看到技术债或坏模式，第一反应就是写一条 lint 规则：先止血，让它不再扩散，再让智能体慢慢清理。〔Remy；作者 X 帖〕
  3. 规则、Bugbot 与 Skill（prose 文字层）：从硬约束变成了指导。大多数时候有用，但智能体可能忘了读，驾驶它的人也可能忽略。作者的帖子说：尽量少用，但一定要用 /create-verification-skill。〔Remy；作者 X 帖〕
  4. 风格指南与人工评审：最难扩展。PR 速度一上来，就不可能逐行看。人工评审适合用来发现缺口，然后把时间投到上面几层。同一类评审意见反复出现，说明它还卡在这一层，没有被吸收进架构、lint 或规则。〔Remy；作者 X 帖〕
  5. 验证类 Skill：能拿出“正确性”的经验证据（这条路径真的端到端跑通了），但不能自动证明性能好、代码写得好。性能要另有指标和遥测，代码质量要另一类 Skill。〔Remy〕
  • 光谱的另一头是形式化方法（Lean、TLA+）。她在演讲里说自己还没走这条路，认为这仍是难题，但验证类 Skill 不靠形式化方法也能走很远。〔Remy〕⚠️ 演讲之后她在 pstack 里加了 /create-formal-verification-skill（10 月）和 /statechart，11 月初还说 adversarial review 大多是浪费 token，不如把 token 花在经验验证加形式验证上。这说明她的立场在演讲后又往前走了一步，不属于演讲内容。〔作者 X 帖 2111926622278521253、2117437607940681849〕

5. 案例一：Control Glass，内部的验证 Skill

  • 她在 Cursor 做的第一个 Skill 叫 Control Glass，教智能体用 Chrome DevTools Protocol 启动应用、抓 trace。没有公开页面。〔Remy〕
  • 迭代后定下的结构分两部分：① 放在 Skill 目录里的可复现 CLI，不让智能体每次现写脚本，否则脚本会在不同会话之间漂移，同一条性能线量的其实不是一回事；② feature map（功能地图），是她自己起的名字，灵感来自 sitemap：写在仓库里的“应用说明书”，记录有哪些功能、怎么进入、快捷键、该点哪个 DOM 元素，由一组自动化维护。〔Remy〕
  • 两部分缺一不可。内部 Slack 里常见的报告是一张截图加三个问号，有了 CLI 和功能地图，智能体才能可靠地操控应用、看懂请求。团队很快把这类 Skill 当成需要持续维护的关键基础设施。〔Remy〕现在 Cursor 和 SpaceX AI 的每个应用都有一个自动维护的验证 Skill。〔Matt Pocock 访谈摘要 ⚠️ 不同场合〕

6. 案例二：Dune，让捷径成为唯一正确的路

  • Dune 是 Grok Bot 代码库里的客户端框架，没有公开。原则是：智能体爱走捷径，那就让捷径恰好是对的路。这样的代码库会让人写着难受，但适合上下文很少的智能体，也适合将来进来改功能的设计师、PM、CEO。〔Remy〕
  • 例子一：她起初觉得注释无害，后来在 Cursor 看到智能体拿注释当借口，用短期 hack 盖住真正的 bug，于是 Dune 里禁止写注释。〔Remy〕
  • 例子二：Electron 主进程的代码不许进入 renderer。renderer 要守住帧预算（60fps 约 16ms，120fps 约 8ms），Dune 用 import 依赖图把这条边界固定下来。〔Remy〕
  • “园丁”角色：专门盯着代码库里冒出来的杂草，趁没蔓延就掐掉。三个要点：删掉现有技术债（智能体会照抄）；鼓励的模式只留一条铺好的路；看到坏模式先写 lint 规则。〔Remy；Gene Gi〕

7. 外循环：把工具接上就行，不必造“公司大脑”

  • Grok Bot 擅长她说的外循环：接上 Slack、Datadog、Sentry、PlanetScale 等连接器，收集信息、做决策，再自动拉起云端智能体。Routines 可以订阅 Slack 线程或 Sentry 告警，自动开工。〔Remy〕
  • 她不认同要先搭一个复杂的“company brain”，因为智能体本来就擅长用工具。她现场展示了 Cursor 上自动复现 bug、自动开 PR 的截图。〔Remy〕
  • 前提是前几层已经到位。在没锁紧的仓库上跑外循环，只会把垃圾 PR 自动化放大。〔Remy〕
  • pstack 她只是提了一下，没有展开：一个 Cursor 插件，把她自己调试、做功能、做原型的方式写成 Skill，入口是 /poteto-mode（先跑 /setup-pstack）。〔Remy〕

8. 结尾与延伸

  • Gene Gi 的笔记把结尾概括为：随着对智能体的信任提高，让每一步都由智能体来做，逐步把人从回路里撤出来。笔记里还记了一个问题：UI 工作怎么验证，UI 层和数据层怎么解耦。〔Gene Gi〕
  • 演讲后作者发了一份可以直接交给智能体执行的“落地提示”：装上 pstack，新建一个 Project，让它翻你在 Slack 和代码评审里给过的反馈，用 /recall 读你以前怎么引导智能体，用 /correct、/architect 从过去的 commit 里找出最常见的坑，然后提出一个让代码对智能体更友好的重构方案，开工前先用 /sharpen 和 /in-your-own-words 跟你确认。〔作者 X 帖 2111133080526495985〕
  • 10 月 2 日 Matt Pocock 的直播访谈补充了一些演讲里没细讲的做法：抽样评审（不可能尝每道菜）、10 多个“幕僚长”协调智能体全天候工作、pstack 的 full autopilot 模式为每个 PR 派验证智能体去 fuzz 应用后自己合并、早上看 commit 历史，有问题就回滚或加 lint。〔uiuo.nl 访谈摘要〕⚠️ 这些来自另一场访谈，不是这场演讲。

这条思路和她 11 月发的 Grok Bot 团队指南一脉相承：都是少而精、把纠正写成 Skill、能写成脚本的就写成脚本。本站另有一页 刘老板对那篇指南的解读可以对照。她在 cursor/plugins 里开源的 pstack 插件（MIT，含 /poteto-mode、/statechart）大概就是这套“验证 + 沉淀”在工具上的落地 ⚠️ 推断。
