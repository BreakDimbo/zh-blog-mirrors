导读：视频讲了什么（⚠️ 据回复区转述）

作者在帖子里只写了一句标题，没有附文字版要点，同一对话里也没有她本人的自回复。回复区有十几位读者 @Grok 请它总结视频，几条回答说法一致，大意如下，可以当观看前的提纲：

  • 重点不在多开几个智能体，而在信任。先把环境搭到“米其林后厨 / 软件工厂”的程度，让智能体没人盯着也能交出可靠的代码。⚠️
  • 信任来自可验证。给智能体配上验证用的 Skill，比如功能地图（feature map）、能跑真实用户路径的 CLI、trace，让它自己证明结果对不对。⚠️
  • 代码库就是智能体的记忆。智能体会照着已有模式写、挑最短的路走，所以要让最短的路恰好就是对的路：持续清理技术债，用架构、类型和边界让反模式根本写不出来；每纠正一次，就马上沉淀成 lint / CI 规则或者更新 Skill，让同样的问题不再出现；团队里设一个“园丁”，专门盯坏味道、拔杂草。⚠️

以上转述取自 @grok 在回复区的几条回答（2026-11-03），回答本身被截断，不完整。想要准确内容请直接看视频。

这条思路和她 11 月发的 Grok Bot 团队指南一脉相承：都是少而精、把纠正写成 Skill、能写成脚本的就写成脚本。本站另有一页 刘老板对那篇指南的解读可以对照。她在 cursor/plugins 里开源的 pstack 插件（MIT，含 /poteto-mode、/statechart）大概就是这套“验证 + 沉淀”在工具上的落地 ⚠️ 推断。

回复区

  • 最多的是“帮我总结一下”和“求文字稿”，说明这条视频确实缺一份文字版。
  • 有人问 2,500 个是 commit 还是 PR，作者没有回答；原帖写的是 PR。
  • 有人追问：怎么及早发现反模式和绕路写法，靠智能体做评审够不够？也没有得到作者回复。
  • 也有读者说，自己搭智能体工作流时最难的正是“真正的信任”，和视频的主线对得上。

  • ⚠️ “一个月 2,500 个 PR 进生产”是作者自报，没有公开仓库或统计可以核对；也没说明 PR 的规模，以及有多少是智能体自动开的。
