建造始终在线的智能体：官方文章导读

Building always-on agents · 独立中文导读

原作者：William Hu，发布方 Anthropic，发表于 claude.com Resources（Best practices · Claude Platform），原文标注日期 2026-11-13，自称阅读时间 14 分钟。原文：https://claude.com/resources/articles/building-always-on-agents。致谢 Rodrigo Olivares、Michael Segner。本页是独立中文导读，只用短引，不是全文翻译。文章、示意图、动图与设计版权归 Anthropic 或其许可方所有；本页未转载原图、动图或官方分享图。封面为自绘字体图，不含官方标志。如需删除，请提交移除请求。

这是一篇写给要把「始终在线」体验做进自己产品里的人看的实践指南，不是一篇评测，也不是某一款托管产品的说明书。作者把 always-on agents 定义为：有状态、会主动做事，能在多次会话之间保存上下文，并且不必等人盯着才会行动。它们仍然跑在和其他智能体相同的核心循环上；真正不同的，是外面那一层决定它何时醒来、两次运行之间留下什么、以及结果怎样交到用户手里的架构。

文章把最近的回潮归因于模型本身的变化：判断力更好，也更知道何时该向人确认；同时智力在变便宜，长程任务受益更大。Anthropic 自报：在某一项长程编码基准上，Opus 5.5 每完成一项任务的成本比 Opus 5 低 78%，而在常规工作负载上大约低 40% ⚠️。数字链到官方的成本与智力优化文档，本站未打开该文档核对，也未复现评测。客户向他们问的，是怎样把这种体验接进已有产品，或从零做起。

本站已经收过同一条记忆线索上的研究文章《智能体记忆的组成》，以及选型指南《该用哪个 Claude 模型来构建》。前者讲记忆怎样写、怎样整理；后者讲该用哪个模型和哪一档 effort。本篇补的是外围怎么搭。

始终在线，只是一种体验

文章先把名字说清楚。原文是：

An always-on agent is not actually “always on.” This is just a description of the user experience.

— William Hu，Building always-on agents（claude.com，2026-11-13）

它大部分时间在睡，并不消耗 token；只是定期醒来做一段工作。每一段叫做一次 run：收到事件，做完这件事，再把经过写回去。一次 run 发生在一次 session 里，也就是消息和工具调用的记录。做完就再睡，这个循环可以一直转下去。官方配了一张时间线动图，本页不转载；图注的大意是：长睡、短醒，每次醒来都是「事件到达 → 打开或接上一次 session → 跑智能体循环 → 把状态写回，供下次接着用」。

五个原语

外围架构被拆成五件东西：事件收件箱、计时器、记忆、权限、发件箱。下面按原文顺序说。

事件收件箱

多数智能体只在用户发来一条消息时才跑。始终在线的智能体还可以被 webhook、定时任务和后台作业唤醒。若让每个事件源直接去调智能体，两个事件同时到达就可能抢着开两次 run，过程中崩溃也可能把事件丢掉。

所以事件先进入收件箱，再由一个 worker 取走。最简单的版本有三部分：一份持久的事件清单（通常是一张数据库表）、一个写入清单的处理端点（通常是 HTTP）、以及一个读取清单的后台服务。收件箱要记录每条事件的状态，并按来源的唯一标识去重。文章建议先按用户各设一个收件箱，需要更大并行时再拆。

新事件进来时，处理端点写入收件箱并叫醒 worker。接续先前工作的事件（例如用户的回复）应回到已有 session；其余则开一次新的 session。worker 把事件交给智能体循环，等这次 run 结束，再把对应事件标成完成。

文章给了几条实践上的提醒：处理端点要尽快确认收到——有些 webhook 把慢响应当成失败——深度检查（例如提示注入）放到 run 里再做；收件箱才是事实来源，worker 被叫醒后应先从收件箱拉取最新事件，这样中途死掉的 worker 可以由下一个接着重试；同一个收件箱同一时刻只应有一个活动的 worker，以免重复劳动或互相覆盖，中途又来新事件时，可以推到下一次 run、并进当前这次，或者中断再重启；多个待处理事件应尽量合并，例如用户连发几条消息，可以并成一次 run，只回复一次。

计时器

计时器和收件箱一起，才让智能体显得会主动做事。计时器大致分两类：跟进（follow-up）是智能体给自己设的截止时间，例如过一会再看有没有回复；日程（schedule）是按已知节奏重复的任务，例如每天一份简报。

计时器要放在单独的持久存储里，通常是另一张表。收件箱里只应放已经到期、可以立刻动手的事件。跟进和日程可以用相近的字段，但日程还要记下如何复发。

计时器自己不会开一次 run。一个调度器按固定间隔扫描存储，把到期的项目变成收件箱里的事件，再叫醒 worker。跟进到期后标成完成；日程则把下次到期时间推到下一回。调度器可以自建，也可以用现成的持久执行引擎。

记忆

始终在线的智能体要跨许多互不连续的 run 工作，连续性靠记忆。记忆也应有自己的存储。文章举他们产品里的例子：Claude Code 的 auto memory，以及 Messages API 的 memory tool，都做成一个文件目录；用在始终在线的智能体上时，这些目录应落到数据库或对象存储，好让记忆活得比某个 worker 更久。⚠️ 这是原文对自身产品的描述，本页不把它写成对所有实现的规定。

经验法则是：只保存没法再查到的东西。若某项内容已经活在问题跟踪系统之类的别处，就存一个指针，而不是再抄一份。文章建议至少分四类：

  • 用户指示：关于智能体该怎么行事的说明，单独成文件，每次 run 开始时加载。人并不总在场，这些指示必须能带到下一次。
  • 用户笔记：已经了解到的角色、偏好和纠正。可以先用一个文件，变长后再拆成若干小文件；那时每次只预加载一份索引，需要细节时再把单个文件拉进上下文。
  • 已经对用户说过的话：避免重复。可以单独成文件在每次 run 开始时加载，也可以由 worker 带上最近几条对用户的消息。
  • 任务进度：每件进行中的事各有一份进度，写清做了什么、还剩什么，好让下一次 run 接着做。和用户笔记一样，开始时只加载索引，需要时再读具体文件。

官方示范图（本页不转载）把每次 run 开始时加载的文件写成 instructions.md、index.md 和 reported.md，并把 notes/ 与 progress/ 留到需要时再读。智能体在 run 期间写入记忆。图中的文件名是示例，不是必须沿用的约定。

以上都是一次 run 里写下的记忆。此外还可以加上 dreaming：回看过往 session，清理过时条目，并找出只有连看许多次 run 才会出现的模式。细节指向本站已收的《智能体记忆的组成》。

上下文窗口里装什么

动手之前，智能体要先载入系统提示、工具定义和记忆文件。这份起始上下文每次 run 都会带上，所以应尽量精瘦，并使用提示缓存来降低费用。新 session 只带着这份开销和触发本次 run 的事件出发；已有 session 则会带回先前的消息和工具调用。session 太长时，可以压缩较旧的消息，或另开一次 session。两种做法都会丢掉细节，所以需要留下来的东西，应沿途写入记忆。

权限

文章认为，权限是始终在线的智能体风险最大的地方。一次 run 握着用户的访问权，而且本来就是无人值守的。每次工具调用，智能体都要决定：自己继续、拦住，还是等批准。

组件和其他智能体相同，但用法要适应后台工作：

  • 凭证存储：建议的模式是在智能体环境外放一个代理，由代理把密码或访问令牌注入出站请求。智能体发出的请求本身不带真实凭证。这与本库先前记下的「大脑/双手分离」是同一类做法。
  • 自动模式：文章指向 Claude Code 里的 auto mode——用分类器审查较高风险的动作，拦住判定为危险的那些，让模型另找更安全的办法。最重要的决定，仍需要人看一眼。⚠️ 这是对 Claude Code 已有机制的转述，不是一份可独立核对的评测。
  • 推迟的工具调用：Claude Code 可以用 hook 把一次工具调用推迟，等人补一句说明或批准。调用被推迟时，这次 run 结束，session 停在调用中途；请求可通过 MCP Apps 一类的交互卡片展示给用户，用户的答复作为事件回到收件箱，再开一次新的 run，从保存的 session 接着做。等待期间，worker 仍可处理其他事件，智能体不必被卡住。

发件箱

多数智能体把回复边生成边推给用户，人可以跟着看推理、工具调用和成文。始终在线的智能体把大部分工作放在后台，用户拿到的是结果和少量说明，而不是全程逐步展开。

一次 run 的结束只有三种：向发件箱送一条消息；判断什么都不必说；或用推迟的工具调用去要权限、要补充。多数情况下，一个直接把消息送给用户的「发送」工具就够了。只有需要控制发送节奏，或希望在出错后还能恢复时，才值得做正式的发件箱。

发件箱是另一张待发出消息的表，调度员（dispatcher）相当于收件箱那边的 worker：读出待发送的消息，决定交哪些，再送给用户。推迟调用的请求可以走发件箱，也可以直接出现在界面里。

比投递机制更要紧的，是发送的数量。发得太多会吵，发得太少又会漏掉用户该知道的事。文章建议用评测来找平衡，并认为实践上最好先偏安静，再逐渐赢得更多注意力。

这五件东西怎样接在一起

每次 run 都从收件箱里的一个事件开始，无论它来自用户消息、webhook 还是计时器。worker 取到事件后，在新的或已有的 session 里叫醒智能体。智能体先读记忆作为基线，在权限范围内行动，再把学到的写回记忆。run 结束后把一行写入发件箱，由调度员交给用户。

它们构成一个循环：一次 run 可以给自己设一枚计时器，稍后再把自己叫醒；用户对消息的答复，会作为事件回到收件箱。单次 run 很短，循环本身可以一直转，这才让人觉得它始终在线。官方另有一张把五个原语接在一起的动图，本页不转载。
